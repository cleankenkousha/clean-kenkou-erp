# 02_System Design Book

## 第1章：システムアーキテクチャ（全体構成）

### 1.1 全体像

Clean KENKOU ERPは、モダンなWeb技術とBaaS（Backend as a Service）、そしてAIを組み合わせた「サーバーレス構成」を採用します。これにより、インフラ管理の手間をなくし、開発スピードと拡張性を最大化します。

* **Frontend (ユーザー画面)**
  * **React + TypeScript** : 型安全で保守性の高いコンポーネント指向UI。
  * **Tailwind CSS** : 01_UIUX Design Bookに準拠した高速なスタイリング。
* **Backend (データベース＆認証)**
  * **Supabase** : PostgreSQLベースのデータベース。リアルタイム通信、ユーザー認証、ファイルストレージ（写真やPDFの保存）、およびRow Level Security (RLS) による強固なアクセス制御を担当。
* **AI Integration (AI連携層)**
  * **OpenAI API (ChatGPT等)** : 顧客との電話内容の要約、OCR（書類読み取り）、音声入力のテキスト化、およびAIアシスタント機能のバックエンドとして機能。
* **External Integration (外部連携)**
  * **牛若丸 (既存システム)** : CSVエクスポート等の手法を用い、定期回収の顧客データや実績データを非同期でERP側（分析DB）に取り込む（将来Phaseでの実装）。

## 第2章：データモデル概念（Job-Centric Architecture）

### 2.1 案件（Job）中心設計

本システムは、すべての業務アクションが「案件（Job）」レコードに紐づく設計とします。顧客単位ではなく、「1回の依頼＝1つのJob」として管理することで、受付から請求までの追跡を容易にします。

* **Customer (顧客)** : 企業名、担当者、連絡先、住所、過去の取引履歴。
* ⬇️ 1人の顧客が複数の案件を持つ (1:N)
* **Job (案件)** : 受付日時、依頼内容、希望日、ステータス、担当者。**（システムの中心）**
* ⬇️ 案件に紐づく詳細データ群
* **Quote (見積)** : 金額、明細、有効期限。
* **Spot Collection (スポット回収実績)** : 実際の回収日、品目、重量/数量、現場写真（Supabase Storage）。
* **Invoice (請求)** : 請求日、支払期日、入金ステータス。

## 第3章：状態遷移図（ステータス管理）

### 3.1 案件（Job）のライフサイクル

案件は発生（電話受付）から完了（請求・入金）まで、一方通行を基本として以下のステータス（状態）を遷移します。このステータスが、ダッシュボードのカンバンボードの「列」と連動します。

1. **受付済 (Received)** : 電話等で依頼を受け付けた直後の状態。詳細未定。
2. **見積中 (Quoting)** : 現地確認や見積書を作成している段階。
3. **手配済 (Arranged)** : 見積が承認され、回収の日程と車両/担当者が確定した状態。
4. **回収完了 (Collected)** : 現場での回収作業が終わり、実績（重量や写真）が登録された状態。この時点で請求可能となる。
5. **請求済 (Billed)** : 請求書が発行された状態。
6. **完了 (Completed)** : 入金が確認され、すべてがクローズした状態。

* **例外ステータス** :
* **保留 (Pending)** : 顧客からの連絡待ちなど、進行が止まっている状態。
* **キャンセル (Cancelled)** : 途中で依頼が取り消された状態。

## 第4章：権限とロール (Roles & Security)

### 4.1 ユーザーロール定義

SupabaseのRow Level Security (RLS) を利用し、役割に応じたデータアクセス制御を行います。

* **Admin (管理者/経営層)**
  * 権限: システムの全機能・全データへのアクセス、ユーザー管理、経営ダッシュボードの閲覧、マスターデータ（単価や品目）の変更。
* **Operator (受付・事務・配車担当)**
  * 権限: 案件の作成・編集、見積・請求の作成、顧客データの管理。システム設定や他のユーザー権限の変更は不可。
