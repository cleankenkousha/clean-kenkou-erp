# 08_Test Design

## 第1章：テスト基本方針 (Test Philosophy)

### 1.1 重点主義（コア業務の保護）

本プロジェクトは、開発スピードと保守性のバランスを取るため、すべてのコードに対して100%のテストを書くことはしない。その代わり、**「業務が止まる致命的なバグ」を防ぐための最重要フローにテストのリソースを集中させる。**

### 1.2 自動テストと手動テストの切り分け

* **自動テスト（プログラムによる自動検証）** : データベースの権限（RLS）、金額計算、案件のステータス遷移など、絶対に間違えてはいけない「裏側のロジック」に適用する。
* **手動テスト（人間による操作検証）** : UI/UX Design Bookで定めた「電話受付30秒以内」「キーボード操作の快適さ」など、人間の感覚に依存する部分は、定期的な操作テストで検証する。

## 第2章：テストの分類と技術スタック

### 2.1 単体テスト (Unit Testing)

* **ツール** : Vitest (または Jest)
* **対象** :
* 金額や消費税の計算ロジック。
* 日付の計算（期限超過の判定など）。
* AIへのプロンプト生成や、JSONレスポンスの解析処理。

### 2.2 結合テスト・セキュリティテスト (Integration & Security Testing)

* **ツール** : Supabaseローカル環境 / pgTAP
* **対象** : Supabaseの Row Level Security (RLS) が正しく機能しているか。
* 例：「オペレーター権限でログインした場合、管理者の設定データを上書きできないこと」を自動テストで証明する。

### 2.3 E2Eテスト (End-to-End Testing)

* **ツール** : Playwright
* **対象** : ユーザーが実際にブラウザを開いて操作する「一連のハッピーパス（正常な業務フロー）」。
* 例：「ログイン → 電話受付（新規案件作成） → スポット回収完了 → 請求書発行」までの流れが、エラーで止まらずに最後まで通るか。

## 第3章：重点テストシナリオ (Key Test Scenarios)

Business Rules Book (03) で定めた業務ルールが守られているかを確認する。

### 3.1 フェイルセーフ（状態遷移のブロック）

* **テスト項目** : 「回収実績（スポット回収）」が未入力の状態で、案件のステータスを「請求済」に変更しようとした時、システムがエラーを出してブロックするか検証する。

### 3.2 UI/UXパフォーマンス（受付30秒ルール）

* **テスト項目** : コマンドパレット（Ctrl+K）を開き、キーボード操作のみで新規案件作成画面に遷移し、必須項目を入力して保存するまでの一連の動作が、エラーなく瞬時に行えるか検証する。

## 第4章：AI機能のテスト方針 (Testing AI)

AIは毎回同じ回答を返すとは限らないため、通常のプログラムとは異なるテストアプローチを取る。

### 4.1 フォーマットとフォールバック（代替）の検証

* **テスト項目** : AI（Edge Function経由）がエラーを返した場合や、JSONの形式が崩れていた場合に、システムがクラッシュせず「AI機能は現在利用できません」と静かにフォールバック（手動入力モードへの切り替え）するか検証する。
* **ハルシネーション耐性** : 存在しない顧客の履歴予測を要求した場合に、AIが架空のデータを捏造せず、適切に「予測不能」として返すかを確認する。
